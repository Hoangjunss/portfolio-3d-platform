**Goal:** On push to the default branch, run the full test suite, build and publish both images
to GHCR, then update the VPS over SSH — with a rollback that does not require a rebuild.

**Architecture:** Three jobs — `test` gates `build` gates `deploy`. Images are tagged by commit
SHA, the VPS pulls that tag, and `latest` is a moving alias for convenience only.

**Tech Stack:** GitHub Actions, GHCR, Docker Compose, SSH.

**Spec:** `docs/superpowers/specs/2026-09-19-portfolio-3d-platform-design.md`

**Depends on:** `2026-09-19-15-docker.md` — specifically the `image:` keys and the `IMAGE_TAG`
variable. A compose file with only `build:` makes this entire plan a no-op (Z-21).

## Global Constraints

- The `deploy` Linux user and its SSH key are a **different identity** from `claude-debug` in plan 18. The deploy key may run `docker compose`; the debug key may only read logs and status. Neither plan may merge them.
- Secrets never appear in the repository, in workflow logs, or in `docker-compose.yml`.
- No comments restating what code does; only comments explaining non-obvious "why".

---

## Decisions settled during plan review

- **(a) The trigger branch is `master`.** `git branch -a` shows exactly one branch, `master`,
  and `origin/HEAD -> origin/master`. The old copy of this plan triggered on `main`, a branch
  that has never existed here, so the workflow would simply never have run — and it would have
  looked like nothing was wrong, because a workflow that does not trigger reports no failure.
- **(b) Tests gate the deploy.** This project runs mutation checks on every plan and refuses to
  trust a "complete" report — and the old pipeline shipped to production without executing a
  single test. `build` needs `test`; `deploy` needs `build`.
- **(c) Images are tagged by commit SHA, not only `latest`.** Rollback then costs one
  `IMAGE_TAG=<old-sha> docker compose up -d` instead of a rebuild from an unknown source state.
- **(d) Secrets reach the VPS as a `.env` file written by the deploy job**, not baked into the
  compose file or the image. Plan 15's compose uses `${VAR:?}` so a missing value stops the
  deploy loudly instead of starting a half-configured stack.
- **(e) The VPS never builds.** It receives `docker-compose.yml` and pulls published images. The
  source tree is not copied there, which is why `build:` keys must not be the only way to
  resolve a service.

### Task 0: Close AC-01 — delete the dead ACME path (do this first)

From `docs/reviews/2026-09-20-code-review-plan-16.md`. An error in plan 16's text, not in what
was implemented from it.

- [ ] **Step 0.1: Remove the acme-challenge block from `nginx/conf.d/00-redirect.conf`**

The block currently reads:

```nginx
location /.well-known/acme-challenge/ {
    root /var/www/certbot;
}
```

Two things are wrong with it at once. `/var/www/certbot` is **not mounted** into the nginx
container — plan 15 mounts only `./nginx/conf.d`, `./templates-static`, `./nginx/certs` and
`media-data` — so the path 404s. And it would never be used anyway: the certificate is a
**wildcard** (`*.portfolio.com`), and wildcards can only be issued through **DNS-01**. The
`/.well-known/acme-challenge/` path exists solely for HTTP-01.

Left in place it actively misleads: an operator reading the config will configure certbot for
webroot HTTP-01 and fail for a reason that is invisible in this file.

Delete the location block and replace it with a comment stating where certificates actually come
from:

```nginx
# Certificates are wildcard (*.portfolio.com), which ACME can only issue over DNS-01 -- there is
# deliberately no HTTP-01 webroot here. Issuance and renewal happen outside the container; see
# docs/ops/ci-cd-secrets.md.
server {
    listen 80 default_server;
    server_name _;

    location / {
        return 301 https://$host$request_uri;
    }
}
```

- [ ] **Step 0.2: Note the manual certificate step in the ops doc**

`docs/ops/ci-cd-secrets.md` is created in Step 3 below. Make sure it carries a short section
saying wildcard issuance and renewal are a manual DNS-01 procedure that this pipeline does not
perform, so nobody goes looking for it in the workflow.

- [ ] **Step 0.3: Commit**


### Task 1: GitHub Actions CI/CD — test, publish, deploy

**Files:**

**Interfaces:**

- [ ] **Step 1: Create `deploy/deploy.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail

cd /opt/portfolio-3d-platform

# IMAGE_TAG is written into .env by the deploy job. Pinning to a SHA is what makes rollback a
# one-liner instead of a rebuild from a source tree this host does not have.
docker compose pull
docker compose up -d --remove-orphans

# Fail the deploy loudly if the backend did not come back up, rather than leaving CI green over
# a crash-looping container.
for _ in $(seq 1 30); do
  if curl -fsS http://localhost/api/public/templates >/dev/null 2>&1; then
    docker image prune -f
    echo "deploy ok"
    exit 0
  fi
  sleep 5
done

echo "backend did not become healthy within 150s" >&2
docker compose logs --tail=100 backend >&2
exit 1
```

- [ ] **Step 2: Create `.github/workflows/deploy.yml`**

```yaml
name: Deploy

on:
  push:
    branches: [master]

env:
  REGISTRY: ghcr.io
  IMAGE_PREFIX: ghcr.io/${{ github.repository }}

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          java-version: "21"
          distribution: temurin
          cache: maven

      - name: Backend tests
        run: mvn -B -f backend/pom.xml test

      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
          cache-dependency-path: frontend/package-lock.json

      - name: Frontend tests and build
        working-directory: frontend
        run: |
          npm ci
          npx vitest run
          npm run build

  build:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push backend image
        uses: docker/build-push-action@v6
        with:
          context: ./backend
          push: true
          tags: |
            ${{ env.IMAGE_PREFIX }}/backend:${{ github.sha }}
            ${{ env.IMAGE_PREFIX }}/backend:latest

      - name: Build and push frontend image
        uses: docker/build-push-action@v6
        with:
          context: ./frontend
          push: true
          # NEXT_PUBLIC_* is inlined at build time (plan 15 decision (a)). Omitting this arg
          # bakes the localhost fallback into the client bundle and every visitor's browser
          # calls their own machine -- with no error anywhere in CI or in the container logs.
          build-args: |
            NEXT_PUBLIC_API_BASE_URL=${{ secrets.PUBLIC_API_BASE_URL }}
          tags: |
            ${{ env.IMAGE_PREFIX }}/frontend:${{ github.sha }}
            ${{ env.IMAGE_PREFIX }}/frontend:latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Copy compose file and deploy script to the VPS
        uses: appleboy/scp-action@v0.1.7
        with:
          host: ${{ secrets.VPS_HOST }}
          username: deploy
          key: ${{ secrets.VPS_DEPLOY_SSH_KEY }}
          source: "docker-compose.yml,deploy/deploy.sh"
          target: /opt/portfolio-3d-platform

      - name: Write .env and run the deploy script
        uses: appleboy/ssh-action@v1.0.3
        env:
          IMAGE_TAG: ${{ github.sha }}
        with:
          host: ${{ secrets.VPS_HOST }}
          username: deploy
          key: ${{ secrets.VPS_DEPLOY_SSH_KEY }}
          envs: IMAGE_TAG
          script: |
            set -euo pipefail
            umask 077
            cd /opt/portfolio-3d-platform
            cat > .env <<EOF
            IMAGE_TAG=${IMAGE_TAG}
            DB_PASSWORD=${{ secrets.DB_PASSWORD }}
            JWT_ACCESS_SECRET=${{ secrets.JWT_ACCESS_SECRET }}
            ANALYTICS_IP_HASH_SECRET=${{ secrets.ANALYTICS_IP_HASH_SECRET }}
            NEXT_PUBLIC_API_BASE_URL=${{ secrets.PUBLIC_API_BASE_URL }}
            SMTP_HOST=${{ secrets.SMTP_HOST }}
            SMTP_PORT=${{ secrets.SMTP_PORT }}
            SMTP_USER=${{ secrets.SMTP_USER }}
            SMTP_PASSWORD=${{ secrets.SMTP_PASSWORD }}
            EOF
            bash deploy/deploy.sh
```

`umask 077` before writing `.env` so the secrets file is not world-readable on the VPS.

- [ ] **Step 3: Document the required secrets in `docs/ops/ci-cd-secrets.md`**

Not under `docs/superpowers/plans/` — it is operational documentation, not a plan, and anything
that lists plans would miscount it.

```markdown
# CI/CD Secrets

Repository secrets required by `.github/workflows/deploy.yml`.

## Deployment target
- `VPS_HOST` — the VPS's public IP or hostname.
- `VPS_DEPLOY_SSH_KEY` — private key for the dedicated `deploy` Linux user. Distinct from
  plan 18's `claude-debug` key: this one may run `docker compose`, that one may only read
  logs and status.

## Application secrets
Generate each with `openssl rand -base64 32`. The backend refuses to start in the `prod`
profile if any still holds its development default (plan 15's `SecretsGuard`).

- `DB_PASSWORD`
- `JWT_ACCESS_SECRET`
- `ANALYTICS_IP_HASH_SECRET` — keyed hash for `analytics_events.ip_hash`. Anyone holding it
  can reverse every stored IP hash.
- `PUBLIC_API_BASE_URL` — e.g. `https://api.portfolio.com`. Used **twice**: as a build arg for
  the frontend image, and in the VPS `.env`. Both must agree.

## Mail (optional)
`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`. Leaving these unset means lead
notification emails are silently dropped while the leads themselves still save.

`GITHUB_TOKEN` needs no setup — Actions provides it, and the `build` job's
`permissions: packages: write` is what lets it push to GHCR.

## Rollback
Images are tagged by commit SHA. To roll back, SSH to the VPS and run:

    cd /opt/portfolio-3d-platform
    sed -i "s/^IMAGE_TAG=.*/IMAGE_TAG=<previous-sha>/" .env
    docker compose up -d
```

- [ ] **Step 4: One-time VPS preparation (manual, document the result)**

```bash
sudo mkdir -p /opt/portfolio-3d-platform/{nginx/conf.d,nginx/certs,templates-static}
sudo chown -R deploy:deploy /opt/portfolio-3d-platform
```

`nginx/conf.d` and the certificates come from plan 16 and are **not** copied by this workflow —
they change rarely and one of them contains private keys. Note in `docs/ops/ci-cd-secrets.md`
that changing an nginx config is a manual step.

Also log the `deploy` user into GHCR once so `docker compose pull` can read private packages:
`echo <PAT> | docker login ghcr.io -u <user> --password-stdin`.

1. `act push -W .github/workflows/deploy.yml --job test` locally to confirm the test job's shape.
2. Push a no-op commit to `master`. The run must show **three** jobs in order and the `test` job

   must go red and `build`/`deploy` must be **skipped**, with the previous containers still
   serving. Revert afterwards. A pipeline whose gate has never been observed failing is not a
   gate, and this project has four separate findings that came from exactly that assumption.

  first disk failure loses every lead and every analytics row. That is a real operational risk
