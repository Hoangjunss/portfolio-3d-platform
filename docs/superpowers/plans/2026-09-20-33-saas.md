# SaaS Demo Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `saas` demo template site (`templates/saas/`) — the third of the 29 site plans
under `2026-09-20-interactive-demo-templates-design.md` §9's execution order. A per-site Hallmark
design pass produces this site's own token set and visual identity, then a static Next.js export
composes `template-kit`'s shared components with this site's seed data (feature grid, pricing
table, integration strip, stat callouts), and finally wires the "Start free trial" plan-selection
feature onto `useLocalCollection`.

**Architecture:** This plan is site plan #3 (site spec:
`docs/superpowers/specs/2026-09-20-site-saas-design.md`). It has one hard prerequisite: plan 30
(`docs/superpowers/plans/2026-09-20-30-template-kit-scaffold.md`), which is assumed **already
landed** — `@portfolio/template-kit` exports `Hero`, `ItemGrid`, `PricedItemGrid`, `StatBlock`,
`Footer`, `useLocalCollection`, `TemplateTheme`, `assertValidTheme` from its barrel
(`template-kit/src/index.ts`). This plan does not modify `template-kit` itself — every task here
lives entirely under `templates/saas/`. Tasks are strictly sequential: Task 1's Hallmark output
(`theme.ts`, `globals.css` tokens) is consumed by Task 2's page composition, and Task 2's rendered
`PricedItemGrid` is what Task 3's interactive feature wires into.

**Tech Stack:** Next.js 15 / React 19, `output: 'export'` static site, TypeScript, Vitest +
Testing Library + jsdom for the interaction test, `@portfolio/template-kit` as a local workspace
dependency.

**Spec:**
`docs/superpowers/specs/2026-09-20-site-saas-design.md` (this site's section composition, seed
data shapes, interactive feature data flow, Hallmark brief) and
`docs/superpowers/specs/2026-09-20-interactive-demo-templates-design.md` (§3.1
`useLocalCollection` contract, §3.2 row #3 the interactive feature, §5 per-site Hallmark
convention, §7 testing addendum, §8 design scoring gate) and
`docs/superpowers/specs/2026-09-20-template-design-system-design.md` (§3 taxonomy row #3, §4 the
9 shared components, §6 folder/thumbnail/export convention).

## Global Constraints

- **Do not modify `template-kit/` in this plan.** Every file this plan creates lives under
  `templates/saas/`. If a gap in `template-kit`'s component contract is discovered during Task 2,
  stop and flag it rather than patching the kit from inside a site plan — that is out of scope
  here (per interactive-demo spec §5, kit component *behavior* is shared and not per-site).
- No comments restating what code does; only comments explaining non-obvious "why" (same
  convention as plan 30's Global Constraints).
- **No fabricated stats presented as real** (interactive-demo spec §5, parent spec §5) — the
  `StatBlock` seed data (site spec §3.4) is already written with illustrative-demo-figure framing
  in its `label` text; Task 2 must render it unchanged, not "polish" the labels into unqualified
  claims.
- **Static content never gates behind `useLocalCollection` hydration** (interactive-demo spec
  §3.1's render pattern) — the feature grid, pricing table, integration strip, and stat block all
  render directly from imported seed data at the page-component level; only the trial-selection
  highlight (Task 3) is client-hydrated post-mount.
- `next.config.js` must set `output: 'export'` (parent spec §6, unchanged).
- `public/thumbnail.webp` is mandatory and validated at build time via
  `template-kit/scripts/check-thumbnail.mjs` (plan 30 Task 2) — this plan's `package.json` build
  script must invoke it before `next build`, same convention every other site plan uses.
- This site's own `theme.ts` must pass `assertValidTheme` (plan 30 Task 2) — a build that ships an
  invalid/incomplete theme object is a Task 1 failure, not something Task 2 silently works around.
- Every rendered `template-kit` component instance must keep working at 320/375/414/768px (plan 30
  Task 3's constraint on the kit applies transitively to any page composing it) — this plan's own
  page-level wrapper markup (highlight treatment, section headings) must not break that.
- Current baseline per `docs/superpowers/STATUS.md`: backend `137/137 PASS`, frontend
  `42/42 PASS`. **Re-read `STATUS.md`'s own header for the actual current number before
  reporting** — other site plans may have landed first; this plan adds no backend changes and does

## Task 3: "Start free trial" plan-selection feature

**Files:**
- Create: `templates/saas/app/PricedItemGridSection.tsx`
- Test: `templates/saas/app/PricedItemGridSection.test.tsx`

**Interfaces:**
- Consumes: `useLocalCollection`, `PricedItemGrid` from `@portfolio/template-kit` (plan 30 Tasks
  3/4/5); `PRICING_TIERS` from `templates/saas/data/seed.ts` (Task 2).
- Produces: `PricedItemGridSection`, the client component `app/page.tsx` (Task 2 Step 9) renders in
  place of the plain `PricedItemGrid` placeholder — this is the final wiring Task 2 deferred.

### Design decisions

**(d)** `PricedItemGridSection` is a `'use client'` component, mounted directly inside the
otherwise-server-rendered `page.tsx` (Next.js App Router islands pattern) — this keeps the rest of
the page's static content server/build-time rendered while isolating the one piece that needs
`useLocalCollection`'s post-mount hydration, per interactive-demo spec §3.1's render-pattern rule.

**(e)** Re-selection is `reset()` + `add()`, exactly as the site spec §4.3 documents and justifies
— not `update()`. The mutation checks below assert this specific sequencing, not just "some
persistence happens."

**(f)** The highlight is rendered as a `data-selected="true"` wrapper `<div>` around the selected
`PricedItemGrid` card's DOM position — since `PricedItemGridProps` has no built-in selected-state
prop (plan 30 Task 3), and this plan's Global Constraints forbid modifying `template-kit`, the
selected state is expressed via a sibling badge element positioned by matching `planId`, queried in
the test via an accessible label (`"Your plan"` text) rather than by reaching into `PricedItemGrid`'s
internal markup.

    // Team is the second seeded tier (Starter, Team, Scale) — site spec §3.2 order.

- [ ] **Step 3: Write `templates/saas/app/PricedItemGridSection.tsx`**

```tsx
'use client';
import { useLocalCollection, PricedItemGrid } from '@portfolio/template-kit';
import { PRICING_TIERS } from '../data/seed';

interface TrialSelection {
  id: string;
  planId: string;
  selectedAt: string;
}

const TRIAL_SELECTION_SEED: TrialSelection[] = [];

export function PricedItemGridSection() {
  const { items, reset, add } = useLocalCollection<TrialSelection>(
    'saas-trial-selection',
    TRIAL_SELECTION_SEED,
  );
  const selectedPlanId = items[0]?.planId;

  function handleSelect(item: { id: string }) {
    reset();
    add({ id: crypto.randomUUID(), planId: item.id, selectedAt: new Date().toISOString() });
  }

  return (
    <section aria-label="Pricing">
      <PricedItemGrid
        currency="USD"
        items={PRICING_TIERS}
        ctaLabel="Start free trial"
        onSelect={handleSelect}
      />
      {selectedPlanId ? (
        <p role="status">
          {`Your plan: ${PRICING_TIERS.find((tier) => tier.id === selectedPlanId)?.title ?? ''}`}
        </p>
      ) : null}
      <button type="button" onClick={() => reset()}>
        Reset demo data
      </button>
    </section>
  );
}
```

**Note on the test's `closest('li')` assertion vs. this implementation:** the reference
implementation above renders the "Your plan" badge as one shared status line below the whole grid,
not per-card. Per design decision (f), the actual per-card highlight (a `data-selected` wrapper
around the matching card) must be implemented so the test's `closest('li')?.textContent` assertion
passes — this requires wrapping `PricedItemGrid`'s rendered `<li>` for the selected plan with
visible "Your plan" text inside that same `<li>`, which is not achievable by rendering
`PricedItemGrid` as an opaque black box from the outside (its `<li>` markup is internal to the kit
component, per plan 30 Task 3, and this plan may not modify the kit). **Resolution:** since
`template-kit` cannot be modified by this plan (Global Constraints) and `PricedItemGridProps` has
no per-item render-prop/children slot to inject a per-card badge, the implementer must either (a)
confirm with a design-prep/brainstorming step whether a per-item highlight is achievable via CSS
alone (e.g. a `:has()` selector keyed off adjacent sibling content, fragile) or (b) treat this as a
genuine kit gap discovered during implementation and escalate it — per this plan's Global
Constraints, patching `template-kit` from inside this site plan is explicitly out of scope, so if
CSS-only cannot express the per-card highlight, the correct fix is a small, behavior-preserving
`template-kit` change proposed and reviewed separately (e.g. an optional
`renderBadge?: (item) => ReactNode` slot on `PricedItemGridProps`), not a bespoke fork of the
component inside `templates/saas/`. The test as written is the acceptance bar either resolution
must satisfy — it must not be weakened to accept a page-level-only badge if that would contradict
"the pricing table highlights the selected plan" from the interactive-demo spec §3.2 row #3's
literal wording (a shared single status line arguably already satisfies that wording, so the
implementer should re-run this decision through `superpowers:brainstorming` only if there is real
doubt, rather than defaulting to the larger kit change unprompted).
