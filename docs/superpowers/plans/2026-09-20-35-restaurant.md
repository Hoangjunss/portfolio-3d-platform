# Restaurant Site (`restaurant`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `restaurant` demo site (interactive-demo taxonomy #5, `display_order` 5) as a
standalone static-export Next.js app under `templates/restaurant/` — a real Hallmark design pass,
the static Hero/menu/Footer page, and the "Reservation form → Your reservations list" interactive
feature backed by `useLocalCollection`.

**Architecture:** This is one of the 29 site plans in
`docs/superpowers/specs/2026-09-20-interactive-demo-templates-design.md` §9 ("plans 31-59"),
numbered 35 in this repo's plan log. **Hard prerequisite: plan 30 must be complete** —
`@portfolio/template-kit` (`Hero`, `PricedItemGrid`, `InquiryForm`, `Footer`,
`useLocalCollection`, `TemplateTheme`/`assertValidTheme`) must exist and be importable before Task
2 of this plan can start. This plan does not modify `template-kit` itself — if a task here appears
to need a kit change, that is out of scope (flag it, do not patch the kit from a site plan).

**Tech Stack:** Next.js 15 / React 19 (`output: 'export'`), TypeScript, Vitest + Testing Library +
jsdom for the interaction test, the `hallmark` skill for the design pass. No backend change — this
site is 100% static export + client-side `localStorage`, per the interactive-demo spec's
non-goal ("no template gets a real backend").

**Spec:** `docs/superpowers/specs/2026-09-20-site-restaurant-design.md` (this site's data
shape/content/theme-brief), `docs/superpowers/specs/2026-09-20-interactive-demo-templates-design.md`
(§3.1 `useLocalCollection` contract, §3.2 row 5 interactive feature, §5 per-site Hallmark
convention, §7 testing addendum, §8 design scoring gate), `docs/superpowers/specs/2026-09-20-template-design-system-design.md`
(§4 component behavior/combination example, §6 folder/thumbnail/export convention).

## Task 1: Hallmark design pass

**Files:**
- Create: `templates/restaurant/theme.ts`

**Interfaces:**

- Produces: the token values Task 2's `page.tsx`/CSS consume — `--color-accent`, `--font-display`,
  `--font-body` (or whatever concrete custom-property names the Hallmark session's output maps
  `TemplateTheme` fields onto; see below) plus any additional tokens (spacing scale, motion
  durations/easings) the session decides this site needs, all defined in `globals.css`.

### Design decisions

**(a)** This task is a real design session, not a data-entry step — it invokes the `hallmark`
skill's **greenfield path**, seeded with the site spec's §5 brief (industry mood: intimate
contemporary bistro; starting anchor: warm terracotta/rose, serif display; the 3 reference
directions listed there). The skill's own process (moodboard research, direction selection, token
generation, audit) determines the actual color/type/spacing/motion values — this plan does not
pre-select them, per the "No Placeholders" exception this plan's brief explicitly carved out for
Hallmark's real output.

**(b)** Output must conform to `template-kit`'s open `TemplateTheme` shape (plan 30 decision (f)):
this is not the old fixed 4-cluster enum — the Hallmark session is free to land on any coherent
token set within the warm/serif starting direction (or to justify a deviation, per the master
spec's "a real Hallmark pass may deviate if research points elsewhere" note), as long as
`theme.ts`'s exported object has non-empty `accentHue`, `displayFont`, `bodyFont` string fields
(and any other fields `TemplateTheme` has gained by the time plan 30 ships — re-check the shipped
type before writing this file, do not assume it is frozen at exactly those 3 fields).

**(c)** `globals.css` is where the session's full token set becomes CSS custom properties consumed
by `template-kit`'s components (which read `var(--color-accent)` etc. at render time, not
`TemplateTheme` values directly, per plan 30 decision (i)) — `theme.ts` and `globals.css` must
agree: every custom property a component class (`.tk-hero`, `.tk-priced-item-grid`, `.tk-inquiry-form`,
`.tk-footer`, per plan 30 task 3/5's class names) relies on must have a real value here, not a
missing var falling back to browser default.

```tsx
'use client';
import { InquiryForm, useLocalCollection, type InquiryField } from '@portfolio/template-kit';

export interface Reservation {
  id: string;
  name: string;
  phone: string;
  partySize: number;
  date: string;
  time: string;
}

const reservationFields: InquiryField[] = [
  { name: 'partySize', label: 'Party size', type: 'number', required: true },
  { name: 'date', label: 'Date (YYYY-MM-DD)', type: 'text', required: true },
  { name: 'time', label: 'Time (HH:MM)', type: 'text', required: true },
];

export function ReservationSection() {
  const { items, add, reset } = useLocalCollection<Reservation>('restaurant-reservations', []);

  async function handleSubmit(values: Record<string, string>) {
    add({
      id: crypto.randomUUID(),
      name: values.name,
      phone: values.phone,
      partySize: Number(values.partySize),
      date: values.date,
      time: values.time,
    });
  }

  return (
    <section className="restaurant-reservations">
      <h2>Reserve a table</h2>
      <InquiryForm fields={reservationFields} submitLabel="Reserve" onSubmit={handleSubmit} />

      <h3>Your reservations</h3>
      {items.length === 0 ? (
        <p>No reservations yet</p>
      ) : (
        <ul>
          {items.map((reservation) => (
            <li key={reservation.id}>
              {reservation.name} — {reservation.partySize} guests — {reservation.date} at {reservation.time}
            </li>
          ))}
        </ul>
      )}
      <button type="button" onClick={reset}>Reset demo data</button>
    </section>
  );
}
```
