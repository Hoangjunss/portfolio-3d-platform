# CRM Clinic Demo Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `crm-clinic` demo template site (`templates/crm-clinic/`) — the last of the 29
site plans under the interactive-demo templates program, and the third of the three CRM variants
(parent spec §4.3). Unlike every other site in this program, this is **not** a public marketing
landing page: it is a mock internal dashboard app — a fake "login" screen, then a sidebar-navigated
shell with three screens (Patients / Treatment Pipeline / Activity Log), each backed by
`useLocalCollection` and one of the kit's `RecordTable`/`KanbanBoard` components.

**Architecture:** This plan is plan 59 in the interactive-demo spec's §9 execution order. It has one
hard prerequisite: `2026-09-20-30-template-kit-scaffold.md` must be complete and committed
(`@portfolio/template-kit` built, tested, exporting `RecordTable`, `KanbanBoard`,
`useLocalCollection`, `TemplateTheme`/`assertValidTheme` from its barrel `src/index.ts`). This plan
does not modify `template-kit` itself — it only consumes it, and does not modify the other two CRM
variants (`crm-realestate`, `crm-agency`) — each is an independent plan/repo per parent spec §9.
Because this site's scope is genuinely larger than a landing-page site (3 screens + login + a
cross-screen activity-logging contract), it has **5 tasks, not 3**: Task 1 runs the Hallmark design
session; Task 2 scaffolds the app, the fake-login screen, and the dashboard shell (with placeholder
slots for the three screens, per the precedent in plan 31 Task 2 Step 9); Tasks 3-5 each build one
screen into its slot, wiring the shared `logActivity` helper (created in Task 2) into Tasks 3/4's
mutations; Task 5 also carries the final design-score table per master spec §8.

**Tech Stack:** Next.js 15 / React 19 static export (`output: 'export'`), TypeScript, Vitest +
Testing Library + jsdom for interaction tests, `@portfolio/template-kit` as a local workspace
dependency. No backend change — this plan touches nothing under `backend/`.

**Spec:** `docs/superpowers/specs/2026-09-20-site-crm-clinic-design.md` (UI relabeling, fake-login
behavior, sidebar structure, seed data, activity-log auto-append triggers, Hallmark design brief)
plus the two specs it is scoped by: `docs/superpowers/specs/2026-09-20-interactive-demo-templates-design.md`
(§3.1 `useLocalCollection` contract, §3.3 `KanbanBoard`/`RecordTable` behavior, §4.3 the CRM page
structure/data model, §5 per-site Hallmark requirement, §7 the build+interaction test gate, §8 the
10-criterion design scoring gate, §9 execution order) and
`docs/superpowers/specs/2026-09-20-template-design-system-design.md` (§6 folder/thumbnail/slug
convention, unchanged).

### Design decisions

**(b) `data/seed.ts` holds every type and seed array for this site** — `Contact`, `Deal`,
`ActivityLogEntry`, `SessionState`, and `CONTACTS`/`DEALS`/`ACTIVITY_LOG`/`SESSION_SEED`, exactly as
shaped in `docs/superpowers/specs/2026-09-20-site-crm-clinic-design.md` §4 — imported directly by
every screen, never redefined per-screen.

**(c) Login state goes through `useLocalCollection` like every other collection on this site**, per
spec §3.1 — a single-row collection keyed by a fixed `id: 'session'`, not a bespoke
`localStorage.getItem`/`setItem` pair, so "every interactive feature calls `useLocalCollection`,
never a bespoke storage mechanism" (parent spec §3.1) holds for login state too.

**(d) `resetDemoData()` is the one deliberate exception to (c)** — the "Reset demo data" affordance
must reset *four* independent collections (`session`, `contacts`, `deals`, `activityLog`) and then
return the visitor to the login screen. Because only the currently-mounted screen's
`useLocalCollection` instance is live at any moment (the sidebar unmounts inactive screens, Task 2
Step 9 below), no single component holds all four hooks' `reset()` functions simultaneously.
`resetDemoData()` writes each collection's seed value to its exact storage key in the exact `T[]`
JSON shape `useLocalCollection` itself persists (so a subsequent mount of any hook reads it
identically to a normal seed-write), then calls `window.location.reload()` — a full reload is the
simplest correct way to put every part of the UI (including the currently-active screen) back in
sync with the four freshly-reset keys at once, and naturally re-runs `page.tsx`'s login check against
the now-`loggedIn: false` session row. This function is the *only* place in this site that writes to
`localStorage` outside of a `useLocalCollection` instance, and only for this one cross-cutting
reset-and-log-out affordance — no regular add/update/remove mutation anywhere in this plan bypasses
the hook.

**(e) `public/thumbnail.webp` in this step is a real, valid WEBP file** (placeholder imagery
acceptable, invalid/missing file is not) — same convention as plan 31 Task 2 decision (c); this
site's real thumbnail will eventually be a screenshot of the dashboard shell (parent spec §4.3/§6),
uploaded by an admin later.

```tsx
import { describe, it, expect, beforeEach, vi } from 'vitest';
import { render, screen, fireEvent, waitFor } from '@testing-library/react';
import Page from './page';

beforeEach(() => {
  window.localStorage.clear();

describe('crm-clinic login flow', () => {
  it('shows the login screen on first visit', () => {
    render(<Page />);
    expect(screen.getByRole('button', { name: /sign in/i })).toBeInTheDocument();

  it('any input signs in and shows the dashboard shell', async () => {
    render(<Page />);
    fireEvent.change(screen.getByLabelText(/email/i), { target: { value: 'anything@example.com' } });
    fireEvent.change(screen.getByLabelText(/password/i), { target: { value: 'whatever' } });
    fireEvent.click(screen.getByRole('button', { name: /sign in/i }));

    await waitFor(() => {
      expect(screen.getByRole('button', { name: 'Patients' })).toBeInTheDocument();
    });
  });

  it('reload (simulated by remount) after signing in stays logged in', async () => {
    const { unmount } = render(<Page />);
    fireEvent.click(screen.getByRole('button', { name: /sign in/i }));
    await waitFor(() => expect(screen.getByRole('button', { name: 'Patients' })).toBeInTheDocument());
    unmount();

    render(<Page />);
    await waitFor(() => expect(screen.getByRole('button', { name: 'Patients' })).toBeInTheDocument());
  });

  it('Reset demo data logs the visitor out', async () => {
    vi.spyOn(window.location, 'reload').mockImplementation(() => {});
    render(<Page />);
    fireEvent.click(screen.getByRole('button', { name: /sign in/i }));
    await waitFor(() => expect(screen.getByRole('button', { name: 'Patients' })).toBeInTheDocument());

    fireEvent.click(screen.getByRole('button', { name: /reset demo data/i }));

    await waitFor(() => {
      const stored = JSON.parse(window.localStorage.getItem('crm-clinic-session')!);
      expect(stored[0].loggedIn).toBe(false);
    });
  });
});
```

**(f) `RecordTable`'s row type is a small local view-model (`ContactRow`), not `Contact`

derived.

the row (plan 30 Task 5 Step 7's `<button onClick={() => onEdit(row)}>`); this screen keeps a local
`editingId` state and renders a small `EditPatientForm` beneath the table when set, calling
`update()` (from this screen's own `useLocalCollection<Contact>`) on save.

**(h) The "Add patient" form's field names are distinct from the edit form's** (`newName` vs.
`name`, etc., with distinct label text "Patient name" vs. "Name") specifically so both forms can be
on screen at once (while editing one existing patient) without an ambiguous `getByLabelText` match
in tests or for a real screen reader user.

```tsx
'use client';
import { useState, type FormEvent } from 'react';
import { useLocalCollection, RecordTable } from '@portfolio/template-kit';
import { CONTACTS, ACTIVITY_LOG, type Contact, type ActivityLogEntry } from '../data/seed';
import { logActivity } from '../lib/logActivity';

interface PatientsColumn {
  key: string;
  label: string;
}

const COLUMNS: PatientsColumn[] = [
  { key: 'name', label: 'Name' },
  { key: 'referredBy', label: 'Referred By' },
  { key: 'email', label: 'Email' },
  { key: 'phone', label: 'Phone' },
  { key: 'tagsDisplay', label: 'Tags' },
];

interface ContactRow extends Contact {
  referredBy: string;
  tagsDisplay: string;
}

function toRow(contact: Contact): ContactRow {
  return { ...contact, referredBy: contact.company, tagsDisplay: contact.tags.join(', ') };
}

export function PatientsScreen() {
  const { items, add, update, remove } = useLocalCollection<Contact>('crm-clinic-contacts', CONTACTS);
  const { add: addLogEntry } = useLocalCollection<ActivityLogEntry>('crm-clinic-activity-log', ACTIVITY_LOG);
  const [editingId, setEditingId] = useState<string | null>(null);

  const editingContact = items.find((contact) => contact.id === editingId) ?? null;

  function handleEdit(row: ContactRow) {
    setEditingId(row.id);
  }

  function handleSaveEdit(patch: Partial<Contact>) {
    if (!editingContact) return;
    update(editingContact.id, patch);
    logActivity(addLogEntry, {
      contactId: editingContact.id,
      type: 'patient_updated',
      note: `${editingContact.name}'s record was updated.`,
    });
    setEditingId(null);
  }

  function handleDelete(id: string) {
    const contact = items.find((entry) => entry.id === id);
    remove(id);
    if (contact) {
      logActivity(addLogEntry, {
        contactId: contact.id,
        type: 'patient_deleted',
        note: `${contact.name}'s record was removed.`,
      });
    }
  }

  function handleAdd(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const form = event.currentTarget;
    const formData = new FormData(form);
    const name = String(formData.get('newName') ?? '').trim();
    if (!name) return;

    const newContact: Contact = {
      id: crypto.randomUUID(),
      name,
      company: String(formData.get('newReferredBy') ?? ''),
      email: String(formData.get('newEmail') ?? ''),
      phone: String(formData.get('newPhone') ?? ''),
      tags: [],
    };
    add(newContact);
    logActivity(addLogEntry, {
      contactId: newContact.id,
      type: 'patient_added',
      note: `${newContact.name} added as a new patient.`,
    });
    form.reset();
  }

  const rows = items.map(toRow);

  return (
    <section aria-label="Patients">
      <h1>Patients</h1>

      <form onSubmit={handleAdd} aria-label="Add patient">
        <label>
          Patient name
          <input name="newName" required />
        </label>
        <label>
          Referred by
          <input name="newReferredBy" />
        </label>
        <label>
          Patient email
          <input name="newEmail" type="email" />
        </label>
        <label>
          Patient phone
          <input name="newPhone" type="tel" />
        </label>
        <button type="submit">Add patient</button>
      </form>

      <RecordTable columns={COLUMNS} rows={rows} onEdit={handleEdit} onDelete={handleDelete} />

      {editingContact ? (
        <EditPatientForm contact={editingContact} onSave={handleSaveEdit} onCancel={() => setEditingId(null)} />
      ) : null}
    </section>
  );
}

interface EditPatientFormProps {
  contact: Contact;
  onSave: (patch: Partial<Contact>) => void;
  onCancel: () => void;
}

function EditPatientForm({ contact, onSave, onCancel }: EditPatientFormProps) {
  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const formData = new FormData(event.currentTarget);
    onSave({
      name: String(formData.get('name') ?? contact.name),
      company: String(formData.get('referredBy') ?? contact.company),
      email: String(formData.get('email') ?? contact.email),
      phone: String(formData.get('phone') ?? contact.phone),
    });
  }

  return (
    <form onSubmit={handleSubmit} aria-label={`Edit ${contact.name}`}>
      <label>
        Name
        <input name="name" defaultValue={contact.name} />
      </label>
      <label>
        Referred By
        <input name="referredBy" defaultValue={contact.company} />
      </label>
      <label>
        Email
        <input name="email" type="email" defaultValue={contact.email} />
      </label>
      <label>
        Phone
        <input name="phone" type="tel" defaultValue={contact.phone} />
      </label>
      <button type="submit">Save</button>
      <button type="button" onClick={onCancel}>Cancel</button>
    </form>
  );
}
```

```tsx
'use client';
import { useLocalCollection, KanbanBoard } from '@portfolio/template-kit';
import { DEALS, CONTACTS, ACTIVITY_LOG, type Deal, type ActivityLogEntry } from '../data/seed';
import { logActivity } from '../lib/logActivity';

interface PipelineColumn {
  key: string;
  label: string;
}

const COLUMNS: PipelineColumn[] = [
  { key: 'inquiry', label: 'Inquiry' },
  { key: 'consultation_scheduled', label: 'Consultation Scheduled' },
  { key: 'in_treatment', label: 'In Treatment' },
  { key: 'completed', label: 'Completed' },
];

function formatVnd(value: number): string {
  return new Intl.NumberFormat('vi-VN', { style: 'currency', currency: 'VND' }).format(value);
}

function patientName(contactId: string): string {
  return CONTACTS.find((contact) => contact.id === contactId)?.name ?? 'Unknown patient';
}

export function TreatmentPipelineScreen() {
  const { items, update } = useLocalCollection<Deal>('crm-clinic-deals', DEALS);
  const { add: addLogEntry } = useLocalCollection<ActivityLogEntry>('crm-clinic-activity-log', ACTIVITY_LOG);

  function handleMove(id: string, newStage: string) {
    const deal = items.find((entry) => entry.id === id);
    update(id, { stage: newStage, updatedAt: new Date().toISOString() });
    if (deal) {
      const columnLabel = COLUMNS.find((column) => column.key === newStage)?.label ?? newStage;
      logActivity(addLogEntry, {
        dealId: deal.id,
        contactId: deal.contactId,
        type: 'treatment_stage_changed',
        note: `${deal.title} moved to ${columnLabel}.`,
      });
    }
  }

  return (
    <section aria-label="Treatment Pipeline">
      <h1>Treatment Pipeline</h1>
      <KanbanBoard
        columns={COLUMNS}
        items={items}
        renderItem={(deal) => `${deal.title} — ${patientName(deal.contactId)} — ${formatVnd(deal.valueVnd)}`}
        onMove={handleMove}
      />
    </section>
  );
}
```

### Design decisions

**(l) How Task 3/4's mutations reach this screen, stated explicitly (per this plan's Task
description):** `logActivity` (created in Task 2 Step 10) is the one shared helper every mutation
site calls — `PatientsScreen`'s add/edit/delete handlers (Task 3) and `TreatmentPipelineScreen`'s
`handleMove` (Task 4) each hold their own `useLocalCollection<ActivityLogEntry>('crm-clinic-activity-log',
ACTIVITY_LOG)` instance purely to obtain its `add` function, and pass that into `logActivity(add,
entry)`. Because the dashboard shell (Task 2 Step 13) renders only the active screen and unmounts
the others, there is never more than one component both reading and writing the same
`'crm-clinic-activity-log'` key's React state at once — a visitor who edits a patient, then clicks
"Activity Log" in the sidebar, causes `ActivityLogScreen` to mount fresh and read the now-updated
`localStorage` value via the hook's own `useEffect` (interactive-demo spec §3.1(m)), the same way a
real page reload would. This is why no cross-screen event bus or context provider is needed: the
hook's hydration contract *is* the propagation mechanism.

**(m) `RecordTable`'s `onEdit` is a required prop with no matching feature here** — activity-log
entries are an append-only record of what happened, not user-editable state (spec §4.3 only
describes "auto-appended ... plus manually addable", never "editable"); this screen therefore passes
`onEdit={() => {}}` (documented as intentionally inert, not a missed feature) and reserves
`onDelete` for correcting a mistaken manual entry only.

**(n) The manual "add a note" affordance is a small page-local form, not `InquiryForm`** —
`InquiryForm`'s fixed name/email/phone/message field set (parent spec §3.3 / plan 30 Task 3) doesn't
match a one-field "note text" entry; this screen's own inline form mirrors the pattern already
established for `PatientsScreen`'s "Add patient" form (Task 3 decision (h)) rather than misusing a
kit component outside its contract.

```tsx
'use client';
import { type FormEvent } from 'react';
import { useLocalCollection, RecordTable } from '@portfolio/template-kit';
import { ACTIVITY_LOG, type ActivityLogEntry } from '../data/seed';
import { logActivity } from '../lib/logActivity';

interface ActivityLogColumn {
  key: string;
  label: string;
}

const COLUMNS: ActivityLogColumn[] = [
  { key: 'atDisplay', label: 'Date' },
  { key: 'type', label: 'Type' },
  { key: 'note', label: 'Note' },
];

interface ActivityLogRow extends ActivityLogEntry {
  atDisplay: string;
}

function toRow(entry: ActivityLogEntry): ActivityLogRow {
  return { ...entry, atDisplay: new Date(entry.at).toLocaleString('vi-VN') };
}

export function ActivityLogScreen() {
  const { items, add, remove } = useLocalCollection<ActivityLogEntry>('crm-clinic-activity-log', ACTIVITY_LOG);

  function handleAddNote(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const form = event.currentTarget;
    const formData = new FormData(form);
    const note = String(formData.get('note') ?? '').trim();
    if (!note) return;
    logActivity(add, { type: 'note', note });
    form.reset();
  }

  const sorted = [...items].sort((a, b) => b.at.localeCompare(a.at));
  const rows = sorted.map(toRow);

  return (
    <section aria-label="Activity Log">
      <h1>Activity Log</h1>

      <form onSubmit={handleAddNote} aria-label="Add a note">
        <label>
          Note
          <input name="note" required />
        </label>
        <button type="submit">Add note</button>
      </form>

      <RecordTable columns={COLUMNS} rows={rows} onEdit={() => {}} onDelete={remove} />
    </section>
  );
}
```
